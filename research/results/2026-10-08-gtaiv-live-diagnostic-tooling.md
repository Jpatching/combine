Historical evidence from 2026-10-08. For current task authority and verdict, read

below record this investigation; they do not select new work.

Researched 2026-10-08 against primary documentation and pinned upstream source. This note changes no runtime files, installs no tools and uploads no game evidence. Documented capability, engineering recommendation and runtime qualification are separate claims. Existing desktop automation research is in [the helper comparison](2026-10-08-gtaiv-runtime-helper-alternatives.md).

## Finding

The smallest practical improvement is a retained game process with repeated bounded native checks, plus a separately qualified JS-only reload workflow. Migrating desktop automation or rebuilding GTA in another engine does not directly resolve the current surface guard. For an open-source debugger, **x32dbg** is a credible fallback for observing our own plugin boundary; it is not yet qualified on this installation. These are engineering assessments from the contracts below.

## Closing and reopening

CLEO documents that editing a running JavaScript script reloads it and **restarts that script**. It also documents automatic script start/stop when files are added/deleted. Saving a JS diagnostic therefore need not require restarting the game according to upstream; this is not a verified cleanup guarantee on our installed adapter. [Script lifecycle](https://re.cleo.li/docs/en/script-lifecycle.html), [hot reload](https://re.cleo.li/docs/en/other-features.html).

The upstream changelog identifies 1.5.1 as the September 26, 2026 release. Version 1.5.0 added unloading of scripts spawned through `CLEO.runScript` when their parent reloads. That is script lifecycle behavior, not evidence that native plugin DLLs or command definitions can be safely replaced in a running process. [Changelog](https://raw.githubusercontent.com/cleolibrary/CLEO-Redux/master/CHANGELOG.md).

**Ctrl+R is unverified.** The reviewed configuration, JS API, lifecycle documentation and changelog do not establish that shortcut's meaning or cleanup semantics. Do not substitute it for the documented file watcher or promise it reloads DLLs/definitions. Nor did those sources establish a CLEO JS REPL (an interactive expression console), VS Code attach debugger or remote debugging protocol. This is a bounded evidence gap, not proof that no third-party implementation exists. [Configuration](https://re.cleo.li/docs/en/config.html), [API](https://re.cleo.li/docs/en/api.html).

Our [adapter runbook](https://github.com/Jpatching/combine/blob/b403377481a33e407aeb81b78b8d38984aac4735/tools/gtaiv-skate/README.md) currently requires normal closure before staging and prohibits replacing files while the game runs. It also warns that DLL unload or removing both restoration scripts cannot restore native ownership. Those project instructions remain applicable. Recommendation for a future narrow revision: qualify only an isolated, unmounted diagnostic script's reload, retain the DLL/definitions/watchdog, verify fresh status and restored GTA control after reload, and fall back to normal closure on failed recovery. The present research does not override the runbook.

Even under that runbook, repeated attempts using **already-installed code** do not require closing/reopening between attempts. Use normal on-foot gameplay at the unchanged location, one tagged attempt at a time, with a fixed deadline and a verdict that distinguishes refusal from missing/stale evidence. Keep Session creation/control transfer disabled for a surface-only diagnostic. Restart normally for changed native binaries, loader/configuration qualification or an unrecovered state.

## Tools that explain the native boundary

| Capability | Primary-source evidence | What it can establish |
| --- | --- | --- |
| Narrow CLEO tracing and local log following | `CLEO.debug.trace(true/false)` toggles command tracing. Official docs give PowerShell `Get-Content cleo_redux.log -Wait -Tail 0`. [API](https://re.cleo.li/docs/en/api.html#cleodebug), [log documentation](https://re.cleo.li/docs/en/log.html) | Executed commands and local runtime errors. Trace only the bounded probe; broad tracing adds noise and logging overhead. Keep raw output private and export fixed reason labels. |
| Generated-definition contract check | CLEO needs argument/result counts and types from JSON. SDK `GetXXXParam`/`SetXXXParam` must correspond to definition inputs/outputs. [Definitions](https://re.cleo.li/docs/en/definitions.html), [C++ SDK](https://github.com/cleolibrary/CLEO-Redux/blob/master/docs/en/cpp-sdk.md) | Source/JSON agreement before launching. Does not exercise the proprietary decoder or establish actual GTA query behavior. A separate real-native smoke probe still matters. |
| x32dbg attach and conditional logpoints | Upstream provides a 32-bit debugger; attach targets an existing process. A break condition of `0` permits logging without an interactive stop. Fast resume skips logging when its condition is false. [Repository](https://github.com/x64dbg/x64dbg), [attach command](https://help.x64dbg.com/en/latest/commands/debug-control/AttachDebugger.html), [conditional breakpoints](https://help.x64dbg.com/en/latest/introduction/ConditionalBreakpoint.html) | Arguments/outputs and calling convention at our plugin functions when script records cannot settle them. A debugger still interrupts execution and affects timing; successful observation is not a normal gameplay acceptance run. |

For x32dbg, first map a known function in **our plugin** using its build/symbol information. Do not guess game offsets. Use an idle diagnostic session and detach explicitly: upstream says closing the debugger terminates a process still being debugged. Attachment and permissions on our installation remain untested. [File menu](https://help.x64dbg.com/en/latest/gui/menus/File.html).

CLEO Redux itself is **freeware under an EULA**, not an open-source runtime: the public repository publishes docs, SDK and examples, while its licence reserves rights and does not grant a general source-modification licence. Do not describe SDK visibility as decoder source availability. x64dbg publishes debugger source with its GPLv3-based licence and modification notice. [CLEO repository](https://github.com/cleolibrary/CLEO-Redux), [CLEO licence](https://raw.githubusercontent.com/cleolibrary/CLEO-Redux/master/LICENSE.txt), [x64dbg licence](https://raw.githubusercontent.com/x64dbg/x64dbg/development/LICENSE).

## Is the asset-extraction table the same approach as MW2?

**It describes a different host strategy from our current GTA adapter.** The pinned MW2/Skate project already owns a from-scratch Rust MW2 runtime. It converts the owner's Skate data and embeds a Rust simulation; it is not a general program that turns arbitrary game archives into a working new game. Its published implementation separately handles collision, grind-rail derivation, bone retargeting, board assets and setup. [Pinned upstream explanation](https://github.com/chasmlol/2010-rust-rewrite-mashup/blob/f608f85e407ff1b7689d54a9aafdd16e95711ac4/docs/SKATE.md).

| Proposed table step | What pinned MW2 source actually supplies | GTA implication |
| --- | --- | --- |
| Extract GTA `.img`/`.wtd` | MW2-specific map/static-model collision and its existing renderer | Archive/texture access alone does not establish a playable scene, placements, collision, streaming or GTA gameplay. A GTA importer would be additional work. |
| Generate a Rust/Bevy wrapper | An existing custom MW2 runtime with explicit Skate integration | A wrapper does not replace engine behavior automatically. Hosting GTA assets outside GTA becomes a replacement-engine project. |
| Ingest Skate animation/logic | Already-implemented Rust Skate `Session` plus converted model, animation graphs and settings | Our plugin already links that same pinned Session. Extracting assets is not proof that arbitrary Skate executable logic transfers to Bevy; the existing implementation is the reusable part. |
| Scan rails | Derived rails from actual loaded collision, then passed to Session | Needs trustworthy collision first. Our 25-point flat patch is insufficient for general rails, obstacles or a whole world. |

This comparison is an inference from the actual [MW2 collision extractor](https://github.com/chasmlol/2010-rust-rewrite-mashup/blob/f608f85e407ff1b7689d54a9aafdd16e95711ac4/crates/render_anim/src/skate/collision.rs), [rail extraction](https://github.com/chasmlol/2010-rust-rewrite-mashup/blob/f608f85e407ff1b7689d54a9aafdd16e95711ac4/crates/render_anim/src/skate/rails.rs), [Session boundary](https://github.com/chasmlol/2010-rust-rewrite-mashup/blob/f608f85e407ff1b7689d54a9aafdd16e95711ac4/skate/crates/skate-host/src/physics/bridge.rs), and [current GTA bridge](https://github.com/Jpatching/combine/blob/b403377481a33e407aeb81b78b8d38984aac4735/tools/gtaiv-skate/src/lib.rs). It does not establish GTA extraction feasibility, complete-engine parity or gameplay acceptance. The [existing detailed comparison](2026-10-08-skate-mw2-gtaiv-integration.md) records adapter differences and the known full upstream host-test limitation.

The owner subsequently clarified that the result **need not run inside the actual GTA game**. Reusing the existing upstream host is therefore a plausible design option, rather than assuming a new engine core must be written. Its source already retains a Session per map, bone/camera presentation and a worker; it also rebuilds Minecraft collision through `collision_builder`/`install_collision`. Those are useful existing seams for another scene provider. [Pinned host integration](https://github.com/chasmlol/2010-rust-rewrite-mashup/blob/f608f85e407ff1b7689d54a9aafdd16e95711ac4/crates/render_anim/src/skate.rs).

That option still needs a GTA scene importer. The pinned asset-loader dispatch contains IW4, T5 and IW5 routes, not a GTA route. A bounded search of the exported upstream `crates/`, `docs/` and root manifest found no whole-word GTA/Liberty/RAGE or `.img`/`.wtd` matches. This search supports **no existing GTA importer found in the inspected scope**, not a universal claim about all tools or branches. The precise loading boundary is visible in [pinned loader dispatch](https://github.com/chasmlol/2010-rust-rewrite-mashup/blob/f608f85e407ff1b7689d54a9aafdd16e95711ac4/crates/assets/src/lane/mod.rs). GTA placements, collision, units and rendering/material conversion remain implementation questions; an AI-generated wrapper alone is insufficient evidence.

Assessment: reusing this host could avoid GTA native-return decoding and supply a more direct collision/presentation interface, while creating importer work. Keeping GTA minimizes scene reconstruction but retains the native integration boundary. To compare costs, a small imported scene with its real collision and visible Skate pose would be more informative than a whole-city promise. The owner's clarification opens that design discussion; no importer, engine migration, runtime adoption or issue closure was performed here. Issue #20 remains open, and its present reproduction stopping point is unchanged.

For the owner's further clarification, **GTA IV with Skate physics/mechanics**, the recommendation depends on which GTA behavior must survive. If driving, traffic, pedestrians, missions and the live city matter, prefer the offline GTA in-process host and reuse the existing Session: rebuilding those GTA systems in the MW2 host is additional work with no supplied implementation. The consequential next seam is authoritative world collision and animation/presentation, rather than more flat-plane guard iterations. The plane diagnostic establishes one refusal; it is not a world solution. If a GTA-derived city to skate around is sufficient, extending the existing Rust host with one GTA scene importer is a credible alternative and merits a small comparison prototype. This is a design recommendation based on the source boundaries above, not a verified performance/cost comparison. No claim is made that OpenIV or CodeWalker exports a ready, compatible GTA IV collision/world package; exporter compatibility and output sufficiency were not established by this research.
