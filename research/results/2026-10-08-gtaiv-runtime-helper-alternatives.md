# Open-source alternatives to the GTA IV runtime helper

Historical evidence from 2026-10-08. For current task authority and verdict, read
[the current context](../../docs/HANDOFF.md) and its linked live issue. Recommendations
below record this investigation; they do not select new work.

Research date: 2026-10-08. Primary-source desk research only; no candidate was installed or tested against GTA IV. Scope: our combined status/input/OCR setup, stronger agent desktop control, native debugging and orchestration from WSL. The owner's follow-up broadened the question beyond keyboard automation; the cross-game integration architecture is investigated separately.

## Finding

**Windows-MCP is the strongest practical candidate for broader agent control of this Windows desktop. Airtest is the strongest candidate for repeatable visual game tests; AutoHotkey v2 is the smaller keyboard alternative. A debugger can inspect our native call boundary. None replaces game-specific state assertions.** These are assessments of documented capabilities, not verified superiority on our installation.

For #20, retain the current native JSON status and guarded input while diagnosing mounting. A tool migration would change the test apparatus without proving whether the player actually mounted. Consider Airtest later if maintaining many visual scenarios becomes costly.

## A larger improvement than another keyboard helper

There are three distinct jobs: navigate the desktop, repeat a scenario, and explain the game's internal failure. A single desktop agent can make the first job much easier. The third needs a game adapter or debugger. Treating visible navigation as proof of game state would weaken our verdict.

## What we need next

Recommendation, not implementation authorization:

1. **Finish the native GTA feedback loop:** preserve native mounted/ground/control checks and distinguish fresh state from missing/stale status. Verify native invocation at our plugin boundary before changing automation. No candidate above supplies a GTA ground oracle.
2. **Reduce repeated Windows setup friction:** prefer a verified isolated runtime copy in a user-writable location, while preserving the original install and required launcher behavior. If that is unsuitable, consider narrowly scoped modification rights for the isolated runtime directory rather than repeated broad elevation. Windows exposes directory-specific access-control management. Copy/rights changes still need environment qualification; none was performed here. [Microsoft icacls](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls).
3. **Qualify Windows-MCP for approved desktop tasks:** Windows-side interactive session, pinned package, local transport, telemetry disabled and tool allowlist. Test foreground selection, DPI/display handling, user takeover and unintended input. Retain our bounded scan-code game actions and real XInput index-0 checks until a replacement proves equivalent.
4. **Use Airtest only when repeated visual tests justify it:** retain native verdicts; add local image assertions without exporting captures. Compare the same scenario against our runner before replacing anything.

Screenshot-aware agent navigation could materially improve recovery from unfamiliar game menus. A local capture server does not make its returned image local to the model: images sent to a hosted AI client leave the machine. Existing repository instructions keep game assets/recordings/private logs outside AI uploads. Using game screenshots for model navigation therefore needs a separate, explicit owner decision about permitted content/destination, or a fully local perception/model route that exports only approved fixed status. This research does not change that boundary or request approval to do so.

Windows consent prompts are a separate constraint. UAC uses the secure desktop by default; ordinary desktop tooling cannot legitimately promise to remove that human step. Keep UAC and secure-desktop protection enabled. Prefer ordinary user-level runtime work; if a particular setup genuinely needs elevation, prepare a bounded operation and let the owner handle Windows consent. [Microsoft UAC behavior](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works).

## What still needs our game adapter

This is an engineering inference from the candidates' interfaces: clicking or recognizing an on-screen board cannot prove a native mounted flag, ground result or scene/cutscene/control gate. Keep the fixed, atomic native status record as the pass/fail authority. Visual recognition can confirm a label or visible transition; it is a separate observation.

Poco is not a ready-made solution to this gap. Its own installation instructions require both the host library and a game/app SDK; unsupported engines need SDK integration. Its supported examples include Unity and cocos2dx, not a drop-in GTA IV state adapter. [Poco integration requirements](https://github.com/AirtestProject/Poco).

Keyboard simulation also cannot establish real gamepad behavior. XInput queries a controller by index 0–3; our index-0 behavior must still be checked with the real controller and native game status. No virtual-controller driver adoption is proposed. [Microsoft XInputGetState](https://learn.microsoft.com/en-us/windows/win32/api/xinput/nf-xinput-xinputgetstate).

All SendInput-based choices share Windows restrictions: injection is limited by process integrity levels and does not reset existing keyboard state. Retain foreground/process guards and explicit release cleanup; replacing the library cannot guarantee the game accepted an action. [Microsoft SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

## Adoption boundary, dependencies and privacy

If adopting Airtest, replace only the Windows visual-scenario runner initially. Keep native state assertions and the input safety wrapper. Run the Windows component in the interactive Windows session; WSL can invoke Windows executables and process compact results. Running a Linux desktop automation backend inside WSL is not evidence that it controls the Windows game. [Microsoft WSL interoperability](https://learn.microsoft.com/en-us/windows/wsl/filesystems#run-windows-tools-from-linux).

Airtest's CLI works without its IDE or Airlab service. Its requirements include OpenCV, NumPy, MSS and pinned pywinauto; evaluate an isolated Windows environment before committing to it. Its reporting features include screenshots/recordings, so preserve our stricter boundary: captures/templates stay private locally, and export only approved fixed labels/status. The requirements list includes `requests`, but that alone is not evidence that test screenshots are uploaded. [CLI and reporting](https://github.com/AirtestProject/Airtest), [Requirements](https://raw.githubusercontent.com/AirtestProject/Airtest/master/requirements.txt).

Maintenance evidence is mixed. AutoHotkey has current v2 release activity and explicitly says v1 is unmaintained. Airtest and pywinauto have public release histories; those do not guarantee our compatibility. PyDirectInput's visible master history ends in February 2021. OculiX identifies itself as the active continuation; that claim is not a game compatibility test. [AutoHotkey releases](https://github.com/AutoHotkey/AutoHotkey/releases), [Airtest releases](https://github.com/AirtestProject/Airtest/releases), [pywinauto releases](https://github.com/pywinauto/pywinauto/releases), [PyDirectInput history](https://github.com/learncodebygaming/pydirectinput/commits/master/).

Future qualification would compare the same short mount/dismount scenario, foreground-loss cleanup and stale/missing-status failure on each candidate. Measure accepted actions and accurate native verdicts, not merely successful API calls. GPU/fullscreen capture, OCR accuracy, timings and GTA IV input acceptance remain unverified.
