# Review the integration approach using REA and Universal Modder

Researched 2026-10-09 for [issue #28](https://github.com/Jpatching/combine/issues/28). This is a source-based recommendation, not an architecture selection or gameplay verdict.

## Finding

**Compare credible end-to-end routes before choosing the next technical question.** Preserve the existing-game host and pinned Skate simulation as the comparison baseline, but do not assume either mount debugging or collision acquisition is the next task. REA and Universal Modder supply ways to investigate; they do not establish a winning architecture. The current adapter's flat-floor limit makes collision a candidate uncertainty, not a demonstrated highest-priority blocker. Choosing the next proof requires comparing loading, simulation access, host geometry, presentation, control and recovery across routes. [Retained geometry implementation](https://github.com/Jpatching/combine/blob/c87e59471c34aff6ffcae5f23b8afc320ca6bd09/tools/gtaiv-skate/src/connection.rs), [mashup guidance](https://github.com/rehan-remade/universal-modder/blob/8370faa8e114baf33acdb23079aff552a7728c4b/skills/mashup-mods/SKILL.md).

The retained goal is offline GTA IV with its ordinary world/gameplay, with the existing Skate simulation owning riding and GTA regaining normal control on dismount. Replacing Skate with similar-looking movement or recreating GTA changes that goal. [Recorded host decision](../../docs/adr/0001-preserve-offline-gta-gameplay.md).

## What the upstream approaches contribute

**REA: ask a bounded question about a shipped artifact when source cannot settle it.** Its skill excludes ordinary complete-source repository analysis. It routes native, managed and packaged targets to analysis providers and requires conclusions to distinguish observations, inferences and unknowns. Native analysis needs a suitable existing provider; installing the skill or CLI does not connect MCP or qualify that provider. For Combine, inspect public SDK/caller source first; consider REA only for an unresolved exact-version native behavior or artifact question. A decompiled function is evidence to interpret, not proof of live geometry correctness or a completed engine recreation. [Pinned REA skill](https://github.com/morluto/rea/blob/f085589957922eaf421db814399e88e415712050/skill-src/reverse-engineer-anything/SKILL.md), [installation/provider boundaries](https://github.com/morluto/rea/blob/f085589957922eaf421db814399e88e415712050/docs/installation.md).

**Universal Modder: choose the lightest route that preserves the requested behavior, then prove the host-specific seams.** Its reconnaissance prefers an existing loader/API before deeper native work. Its mashup guidance distinguishes content conversion, communicating runtimes, host-rendered guest geometry and embedded/rebuilt simulations. It requires ownership, units, timing, communication and recovery contracts. Its knowledge notes explicitly warn that shared languages and a reusable protocol do not remove per-host reverse engineering. These are a better technical decision framework than treating every refusal as a reason to build more machinery. [Reconnaissance](https://github.com/rehan-remade/universal-modder/blob/8370faa8e114baf33acdb23079aff552a7728c4b/skills/game-recon/SKILL.md), [route selection](https://github.com/rehan-remade/universal-modder/blob/8370faa8e114baf33acdb23079aff552a7728c4b/knowledge/techniques/choosing-a-mashup-route.md).

The most relevant knowledge lessons are: select collision representation per consumer; distinguish unknown geometry from known empty space; invalidate moving geometry; measure coordinate/pose freshness; and define a mechanical check before implementing. An **oracle** here means a repeatable check that detects a wrong interpretation. Captures themselves need a freshness check because the guide records plausible stale frames. After roughly three identical failures, preserve findings and change the experiment rather than repeating it. These notes provide investigation methods, not independently verified results for Combine. [Collision guidance](https://github.com/rehan-remade/universal-modder/blob/8370faa8e114baf33acdb23079aff552a7728c4b/knowledge/techniques/collision-and-combat-bridging.md), [oracles](https://github.com/rehan-remade/universal-modder/blob/8370faa8e114baf33acdb23079aff552a7728c4b/knowledge/techniques/oracles-how-agents-know-a-mod-works.md).

## Concrete alternatives and what they prove

These choices are not all substitutes: in-process versus worker is process placement within the same rebuilt-Skate route; improving the GTA scene adapter could apply to either. Original-runtime passthrough and rebuilding the host are different end-to-end routes.

| Route | Useful evidence | Fit and unresolved cost |
| --- | --- | --- |
| Preserve in-process Session | The source already implements the simulation boundary with no process transport. | Valid comparison baseline; host bitness/address space, load time and guest fault containment require measurement. Rust panic catching does not isolate native faults. |
| Preserve optional worker | Existing source separates loading/transport from GTA commands. Universal Modder's rebuilt-engine note discusses worker placement for older 32-bit hosts. | Plausible isolation/iteration benefit; added lifecycle, freshness and input timing complexity. No collision or rendering benefit follows automatically. |
| Improve GTA scene adapter | LibertyCraft reports guest-controlled movement, native GTA rendering and sampled host collision. | Closest host-side prior art; investigate acquisition/control concepts rather than replacing Skate with Minecraft. Exact-version compatibility remains unresolved. |
| Run original Skate alongside GTA | Universal Modder describes two-runtime passthrough as a route. | No reviewed source here demonstrates an original-Skate runtime interface that supplies the required input/collision/pose contract. More processes are not evidence of greater fidelity; do not select this on the tool names. |
| Recreate/import GTA into another host | Prior MW2 source comparison shows why a host owning its scene can supply collision directly. | Requires replacing/reproducing ordinary GTA gameplay and therefore changes the retained goal. |
| Implement Skate-style movement in GTA | Universal Modder describes narrower mechanic transplants. | Could reduce guest-runtime work only by changing the requirement to imitation; original Skate behavior would need separate reference checks. |

Sources for placement and transplantation: [rebuilt guest engines](https://github.com/rehan-remade/universal-modder/blob/8370faa8e114baf33acdb23079aff552a7728c4b/knowledge/techniques/rebuilt-guest-engine-inside-a-host.md), [prior MW2/GTA source comparison](2026-10-08-skate-mw2-gtaiv-integration.md). Architecture comparisons above are engineering inferences, not benchmark results.

LibertyCraft's current README reports GTA IV **1.0.8.0 on Linux/Proton**, IV-SDK, host collision sampling and host rendering. Windows is explicitly untested, and its installer downgrades the game. It also lists thin-object/geometry approximation gaps. Consequently it is valuable source prior art but does not qualify a loader replacement for Combine's **1.2.0.59** baseline. Do not run or copy its install/downgrade procedure as an investigation shortcut. [LibertyCraft](https://github.com/mrborghini/libertycraft).

BullySkate reports Skate 3 physics in Windows Bully 1.200, requires owned game files and exposes native/skating modes. SkateGM reports a Skate simulation in Windows Garry's Mod's x86-64 branch and a toggle in ordinary gamemodes. These are useful evidence that rebuilt-Skate integration has concrete host-specific precedents, not proofs that their loaders, geometry or assets fit GTA. [BullySkate](https://github.com/Faiqie/BullySkate), [SkateGM](https://github.com/the-schwilliam/SkateGM).

SkyCraft reports two real games cooperating while retaining Skyrim quests/saves and returning control for native scripted actions. Its README calls the project experimental and warns about the opening sequence. It supports preserving host systems as an architectural pattern; it does not establish universal mission compatibility. [SkyCraft](https://github.com/chasmlol/SkyCraft).

## Process changes and next discriminating proof

The **GitHub workflow is suitable**: preserve experiments, give slices explicit acceptance, separate source/runtime/owner verdicts, and merge only reviewed accepted work. Branch tidying is housekeeping; it cannot resolve integration feasibility. Keep the preserved experiment and close or archive other branches only after checking unique commits, worktrees and ignored artifacts. This is an assessment of the documented process, not a claim that every historical step followed it. [Repository workflow](../../docs/agents/issue-tracker.md).

For this requirement, #28 defines the question; `research/integration-approach-review` holds the report and handoff; reviewed commits are pushed to a draft PR. After checks and explicit owner approval, squash merge that PR and synchronize main. Accepting the report does not authorize its proposed runtime experiments.

The **technical sequence should shift to comparing routes and their unproven assumptions before selecting a debugging task**. The current flat grid can prove a floor/control handshake; it cannot prove curbs, walls, slopes, furniture or traffic interactions. That limitation alone does not make collision the best next question: a route might first fail exact-version loading, simulation access or control/presentation requirements. Mount could still be a useful proof if it distinguishes viable routes. Reusable tooling should support the chosen question rather than become an end in itself. [Grid contract](https://github.com/Jpatching/combine/blob/c87e59471c34aff6ffcae5f23b8afc320ca6bd09/tools/gtaiv-skate/src/connection.rs), [Workbench](../../docs/WORKBENCH.md).

The following is an engineering decision framework, not a ranking proved by this survey:

| Candidate uncertainty | Evidence we have | Cheapest useful next check and decision it changes |
| --- | --- | --- |
| Does a prior-art integration route fit the retained host/version and goal? | Host-specific examples above; LibertyCraft differs in version/platform. | Inspect its actual loader and host interfaces against 1.2.0.59 support. A mismatch can eliminate direct reuse before a port or runtime trial. |
| Can the real Skate simulation supply the required behavior through a usable interface? | Existing Session source and attributed synthetic trials support the rebuilt simulation; an original-game runtime interface is not established. | Trace each proposed route's input, collision and pose contract in public source. Absence of an accessible contract prevents selecting that route as ready to build. |
| Can GTA present movement and reliably return control? | Existing adapter source and partial dated native observations, but no complete accepted ride. | Map required native operations to version evidence and existing failure observations; propose a bounded control/presentation test only where that result would select or reject a route. |
| Is host collision access sufficient for the intended first proof and longer-term goal? | Current grid is intentionally narrow; other projects report alternative acquisition. | Compare source-backed acquisition and coverage before geometry experiments. A flat-floor handshake and ordinary-city interaction need different evidence; do not silently substitute one for the other. |
| Does process placement materially improve feasibility? | Both current candidates share the same simulation and host responsibilities; worker synthetic trials are partial evidence. | Identify a demonstrated loading, address-space, timing or fault-isolation constraint first. If one exists, compare candidates using the same qualified fixture; a transport rewrite alone cannot settle the other rows. |

**Smallest recommended next check:** a read-only interface audit of the two existing candidates and the closest host-side prior art, LibertyCraft. Compare the public loader, simulation, scene, presentation and recovery interfaces with the retained GTA 1.2.0.59 requirements before writing code. This checks whether there is an evidence-supported cheaper route; it does not presume one exists. For each goal-preserving route, record which capabilities are demonstrated, source-supported only, or unknown; name the assumption that could rule it out and the least costly check of that assumption. Consult the owner only if the route requires changing the goal. A route is ready for a prototype brief only when its required interfaces have a credible path on the selected baseline and its remaining decisive unknown has a bounded test. Lack of evidence is an unknown, not proof of impossibility.

Choose the next experiment by whether its possible outcomes would change the route decision and how cheaply it can resolve that uncertainty. If the evidence cannot distinguish priorities, report that explicitly; do not fill the gap with a familiar bug. This survey does **not** yet establish collision, mounting or worker placement as the winning next question. The separate collision-feasibility research prerequisite on #20 still applies if collision research is selected.

A later experiment brief must identify the exact candidate/version, expected observations, failure/stop conditions and numerical budgets where relevant. Examples include a host-interface check, a geometry proof independent of riding, or a same-fixture comparison of the two existing candidates; none is authorized or selected here. Preserve unchanged failures and change the hypothesis after repeated identical results. Stop live work on stale evidence, unresolved installed identity or failed control restoration. Return the evidence to `grill-with-docs` before selecting an architecture or creating implementation tickets.

No game was launched, installed, controlled or captured for this review. No REA provider, Sandcastle session or Windows readiness was tested; no tracker state or runtime pin changed. No tests/builds were run for the research itself. Prior runtime claims remain attributed to their dated notes. Gameplay, full-city collision, Skate fidelity, final architecture, owner acceptance and release remain unresolved.
