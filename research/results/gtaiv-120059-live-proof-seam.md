Research for [issue #47](https://github.com/Jpatching/combine/issues/47), 2026-10-10. Verdict: **requires-local-proof**; `runtimeVerified=false`.

Recommend the existing **opt-in GTA plugin packet boundary → pinned Skate Session → GTA native pose/camera observations**, paired with an uncut local recording and ordinary GTA recovery actions. The interfaces separate six claims:

| Boundary | What inspected source establishes | What it does not establish |
| --- | --- | --- |
| Keyboard delivery | A helper may insert events into the Windows stream; F6/F8/F9 plugin queries use Windows key state plus foreground checks. | GTA recognition, observer execution or movement. |
| Game input recognition | GTA ordinary walking is an independent native-game response. Riding reads XInput index 0; F8 is a plugin trigger, not GTA's debug-key native. | A Windows key-state result is not proof that GTA's own gameplay input accepted the key. |
| Observer start | `COMBINE_EVALUATION attempt:<n> started` is emitted on entry to playback, before its snapshot/input phases. | A start marker does not imply input was armed or motion occurred. |
| Mounted state | Saved owner handles, native GTA control disabled, camera existing/active/propagating are checked during playback. Status `mounted` is the plugin's ownership flag. | Ownership alone is not an advancing Session or a moving skater. |
| Simulation-driven motion | Adapter sends controls to Session and applies returned root position/heading to GTA; observer reads GTA position/heading and camera. | Source feasibility or small displacement alone does not prove input causality, scale, physical controller delivery, visual presentation or camera usability. |
| Native recovery | Observer checks restored player control and destruction of its saved camera, then optionally walking displacement. | Complete GTA movement/camera/vehicle recovery or acceptance. |

These distinctions follow from the [plugin](https://github.com/Jpatching/combine/blob/fd9f8c4933d3aed193273a2ce5d78fb076886972/tools/gtaiv-skate/plugin.cpp), [riding script](https://github.com/Jpatching/combine/blob/fd9f8c4933d3aed193273a2ce5d78fb076886972/tools/gtaiv-skate/combine_skate.js) and [observer](https://github.com/Jpatching/combine/blob/fd9f8c4933d3aed193273a2ce5d78fb076886972/tools/gtaiv-skate/tests/live-evaluation.js).

**Version and input gate.** The plugin requires a 32-bit pointer size, CLEO host ID 9, executable file-version fields encoding 1.2.0.59, SDK version at least 4 and a seen script callback. That is an exact-version applicability gate, not executable provenance or demonstrated compatibility. Evaluation commands exist only under `COMBINE_SKATE_EVALUATION`. F8/F9 map only action 0/1 to `GetAsyncKeyState`'s high bit when GTA's PID owns the foreground window and identity passes. The observer polls every 100 ms and requires an observed rising edge (`key8 && !held8`). F6 has its own rising-edge foreground gate. [[Plugin gates and key queries](https://github.com/Jpatching/combine/blob/fd9f8c4933d3aed193273a2ce5d78fb076886972/tools/gtaiv-skate/plugin.cpp)]

Microsoft documents that [GetAsyncKeyState](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate) reports currently-down state in its high bit, with zero possible for failed access; its low “recently pressed” bit is unreliable. [GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow) may return null. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) returns inserted event count and is restricted by UIPI; it does not prove application consumption, and its failure result does not identify UIPI as the cause. [XInputGetState](https://learn.microsoft.com/en-us/windows/win32/api/xinput/nf-xinput-xinputgetstate) polls a specified controller index, returning success or device-not-connected. These are general Windows contracts, not GTA IV qualification or an explanation of the recorded failure.

**Bounded packet control.** Evaluation arming requires identity, connected neutral controller 0, GTA foreground, owned ride and no pending reset. Neutral means no buttons, axes within ±4096 and triggers below 30. Profiles last 50–1000 ms: neutral, X push (`0x4000`), X push with left axis −20000, X push with right axis +20000. Application clears on lost permission or expiry; reset, stop, release/rescue clear playback. Expiry returns to physical input. The override occurs immediately before `combine_tick`, not by teleporting in the observer. [[Packet profiles and expiration](https://github.com/Jpatching/combine/blob/fd9f8c4933d3aed193273a2ce5d78fb076886972/tools/gtaiv-skate/evaluation_input.h), [Plugin arming and application](https://github.com/Jpatching/combine/blob/fd9f8c4933d3aed193273a2ce5d78fb076886972/tools/gtaiv-skate/plugin.cpp)]

**Measurement.** F8 playback requests neutral 250 ms, push 750 ms, neutral 250 ms, left 400 ms, neutral 250 ms, right 400 ms and neutral 250 ms: 2.55 seconds of phase time plus scheduling. Each snapshot verifies matching owner handles, uninterrupted gameplay, GTA control disabled, owned camera existing/active/propagating and finite position/camera/heading. It requires start-to-push displacement >0.01 GTA units, left/right heading changes each >0.1 degrees with opposite signs, and camera displacement >0.01 units. It reports `REFUSED` for unavailable input, `UNAVAILABLE` for interruptions/query failures, and `FAIL` for measured predicates that do not pass. It cancels input in `finally`. Game time wraps unsigned; each phase also has an independent Windows elapsed-time deadline of duration +1000 ms. A stopped script scheduler still requires an external deadline. [[Observer phase and verdict logic](https://github.com/Jpatching/combine/blob/fd9f8c4933d3aed193273a2ce5d78fb076886972/tools/gtaiv-skate/tests/live-evaluation.js)]

## Source inference

The best narrow seam keeps OS keyboard triggers at the edge, bounded controller packets inside the adapter, and native observations after pose application. It avoids shared mouse/focus automation and still exercises the real riding path. A later human-controller pass is necessary to prove physical controller delivery: packet playback bypasses that delivery while preserving Session input interpretation and host application. A start marker is the first useful observer signal, not movement proof.

Choose one diagnosis signal: **`observer-start-missing`: zero new `attempt:<n> started` markers within three seconds of a released-then-one-second-held F8 request while fresh focused mounted prerequisites persist.** This is a proposed bounded reproduction of the observed missing marker, not a diagnosis or claim the one-second hold already failed. If mount refuses, status becomes stale, focus changes or ownership ends, classify the attempt as refused/unavailable instead. Do not score it as this failure. Keep `surface-refused:over-0.05-metres` as its own earlier-boundary refusal.

Observer PASS is useful but weak as complete causal evidence: push displacement includes the opening neutral interval, has no stationary counterfactual or velocity/tick check, steering phases also push, and opposite signs do not verify the expected world direction. Passive drift or an unqualified native query could satisfy some predicates. Correlate phase labels with evolving Session tick/pose where already available locally and visible movement; compare a neutral observation before push. If additional fixed-label instrumentation is needed, propose it in #20 and review before any Windows staging. Do not invent telemetry the current observer exposes or interpret “real-input” in its log as physical-device acceptance.
